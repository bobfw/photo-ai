# Project Guide

This is a **Node.js** monorepo managed with pnpm workspaces. `node` is the script runner:

- install: `pnpm install`
- run a package script: `pnpm run <name>` (the root scripts delegate to `apps/photo-ai`)
- run a script in any package: `pnpm --filter <package> run <name>`
- run a standalone script: `node apps/photo-ai/scripts/<file>.ts`

Do not use Bun, npm, or yarn. `pnpm-lock.yaml` is the lockfile; `vp install` / `vp run`
delegate to pnpm in this project.

## Layout

- `apps/photo-ai` — the existing public-facing app.
- New apps go in `apps/<name>` as their own package with its own `package.json`.
- Code shared by more than one app goes in a `packages/<name>` workspace package; never
  import across apps by relative path.
- The root `vite.config.ts` holds the shared lint/format config. Each app's
  `vite.config.ts` holds only its Vite/framework config.

## App: photo-ai

photo-ai（出片）is an **independent, public-facing app**: AI image generation starting with
wedding photos. It runs on Cloudflare Workers with a D1 binding.

- dev: `pnpm dev` (port 5701)
- build / deploy: `pnpm build`, `pnpm deploy`
- local secrets: `apps/photo-ai/.dev.vars` (never commit)
- vouchers: `pnpm voucher:create -- --total 5 --count 10`
- poses: `node apps/photo-ai/scripts/split-poses.ts` splits every series sheet in
  `apps/photo-ai/test-img/` (5 × 4, 20 poses each) into
  `apps/photo-ai/test-img/wedding/poses/<key>/01.png`–`20.png`, removing the printed
  numbers and the grid lines. Upload the regenerated folders to
  `https://image.chupian.date/wedding/poses/`; the app reads poses from that CDN.
  Series keys/titles/outfits live in
  `apps/photo-ai/src/routes/wedding/-internal/services/poses.ts`.

## Mobile

Most users are on phones. Design mobile-first and check the page at phone width (≈390px)
before desktop.

- Touch targets ≥ 44×44px; nothing essential behind hover.
- No horizontal page scroll; keep controls clear of the bottom safe area.
- Prefer native mobile input behavior (e.g. `accept="image/*"` file inputs) over custom pickers.

## Preview (MCP)

`.mcp.json` runs the `chrome-devtools` MCP server against a Chromium browser that is
already listening with remote debugging on `127.0.0.1:9222`. Use it to open the dev
server, screenshot the page at phone width, and read console/network errors instead of
judging UI from source alone.

- The browser must be started with `--remote-debugging-port=9222`; the MCP tools connect
  at session start, so restart Claude Code if the browser was down then.
- Only use the browser MCP—or launch a browser yourself for verification—when the user
  explicitly asks. Never start browser automation on your own.

## Generation Flow

- 用户上传的参考照片由后端签发七牛上传凭证，浏览器直传桶 `chupiandate` 的
  `temp_24h/` 前缀；七牛桶必须配置 1 天生命周期规则自动删除。上传成功后前端调用
  `confirmUpload` 更新 D1 `uploads` 表。签发时先写一条未确认的行，只有确认过的 key
  才能用于生成。前端只保留本地预览，生成请求只传七牛 key。上传凭证签发按凭证限流：
  10 秒 5 次、每天 30 次、累计 100 次（`upload_sign_counters`），未确认的行也受此约束。
- 图片生成走火山 AI MediaKit MaaS 代理异步任务（`mediakit.cn-beijing.volces.com`）：
  后端提交任务拿 `task_id` 落 D1 `generation_tasks`，前端每 10 秒轮询
  `getGenerationTask` 直到完成/失败；接口用前端传入的 `clientToken` 保证幂等。
  服务端同一任务 5 秒内最多推进一次，避免页面加载和客户端轮询重复请求 MediaKit。
- 页面加载时 `getVoucherState` 会推进该凭证最近 24 小时内的 running 任务，前端用
  `activeTasks` 自动续轮询，刷新/第二天重开都不会丢结果；更久或用户不再回访的任务仍
  需要回调/Queue 兜底（MediaKit 结果 URL 也只有 24 小时）。
- 桶按私有空间处理：每次提交生成任务时，后端为参考图签发 30 分钟下载 URL 给
  MediaKit；访问域名和上传域名都写死在 `src/services/qiniu.ts`，线上建议把 `PUBLIC_URL`
  换成 HTTPS 自定义域名。
- 相关 secrets：`QINIU_ACCESS_KEY`、`QINIU_SECRET_KEY`、`ARK_MEDIAKIT_API_KEY`
  （AI MediaKit 的 API Key）。桶固定在华东 z0。

## Cloudflare

- Server code runs on Workers: no filesystem writes, and `process.env` is not available at
  module scope. Read bindings through `env` from `cloudflare:workers`.
- D1 schema is managed by drizzle-kit: `pnpm db:generate` after schema changes,
  `pnpm db:migrate` for local D1, `pnpm db:migrate:remote` for production.
- `apps/photo-ai/wrangler.jsonc` holds the D1 binding;
  `apps/photo-ai/worker-configuration.d.ts` is generated by `pnpm cf-typegen` and must not
  be edited by hand.
- Generated images stay on Ark and D1 stores the URL; the browser reads them through
  `proxy.yumus.cn` because Ark sends no CORS headers, so the canvas can export them.
  Never clean up the D1 rows: `generated_images`, `generation_records` and the
  terms-acceptance fields on `vouchers` are permanent usage and dispute evidence.

## Code Organization

Paths below are relative to an app (`apps/photo-ai/` today). General code lives in shared
modules; anything non-general lives next to where it is used.

- `src/services/` — app infrastructure: database, schema.
- `src/agents/` — Ark (Volcengine) prompts and image generation; keep it Workers-compatible
  (no `sharp`, no static Node `fs` imports).
- `src/components/ui/` and `src/hooks/` — vendored shadcn/base-ui code; do not edit unless
  a change is actually needed.
- Anything specific to a route goes in `src/routes/` beside that route, as a
  `-`-prefixed file or directory (the router plugin skips `-`, so it is not treated as a
  route).
- A route's `-internal/` directory holds logic related to the nearby page. If the page is
  simple or there is nothing worth sharing, keep the page in its route file as a single
  file instead.
- When route-local logic grows, group it in `-internal/` by role, creating only the groups
  the route needs:
  - `components/` — presentational components used only by this route.
  - `services/` — `createServerFn` handlers, data loaders, and route-local constants/types.
- Move a module to `src/{services,components,hooks}/` only when it becomes globally shared
  logic, not just because another route uses it.
- Import shared modules via the package imports declared in `package.json`
  (`#services/*`, `#ui/*`, `#agents/*`, `#hooks/*`, `#lib/*`), not tsconfig path aliases.
- `src/routeTree.gen.ts` is generated; never edit it and keep it excluded from
  formatting/linting. After adding, renaming, or moving route files, run
  `vp -C apps/photo-ai build` first so `routeTree.gen.ts` regenerates before `tsc` runs.
  `pnpm build` runs `tsc && vp build` and would type-check a stale tree.

## Code Style

Do not mark required values as optional. If a field or parameter must always be supplied,
make it required and remove the fallback branches that guard it — e.g. `references:
string[]`, not `references?: string[]` with a default. Only use `?` when callers genuinely
omit the value.

Do not `export` symbols that no other module or script uses. Keep helpers, types, and
constants local until something actually imports them.

# Using Vite+, the Unified Toolchain for the Web

This project is using Vite+, a unified toolchain built on top of Vite, Rolldown, Vitest,
tsdown, Oxlint, Oxfmt, and Vite Task. Vite+ wraps runtime management, package management,
and frontend tooling in a single global CLI called `vp`. Vite+ is distinct from Vite, and
it invokes Vite through `vp dev` and `vp build`. Run `vp help` to print a list of commands
and `vp <command> --help` for information about a specific command.

Docs are local at `node_modules/vite-plus/docs` or online at https://viteplus.dev/guide/.

## Built-in Commands vs Scripts

`vp <name>` runs a built-in command. `vp run <name>` runs a `package.json` script or a
`vite.config.ts` task. Scripts cannot overwrite built-ins, so `vp dev` and `vp run dev` may
do different things. Check `package.json` and `vite.config.ts` first, and run
`vp run <name>` when the project defines a script or task with that name.

## Tool Versions

Run `vp toolchain` to show versions and relationships in the active Vite+ release. Add a
tool name to select part of the graph. For example, run `vp toolchain vite`. Use `--global`
to ignore the local `vite-plus` package. Use `vp why <package>` to show the package-manager
dependency graph.

## Review Checklist
